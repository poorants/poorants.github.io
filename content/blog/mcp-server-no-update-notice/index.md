팀이 같이 쓰는 사내 MCP 를 만들어 돌리는 사람으로서, 가장 자주 한 일은 툴을 만드는 일이 아니었다. 새 판을 낼 때마다 팀에 "업데이트해 주세요" 를 보냈다. 그래도 누가 아직 옛 판을 쓰는지는 따로 확인해야 했다. 새 사람이 오면 300줄짜리 셋업 문서를 건넸다. 실행은 에이전트가 대신 해 주었지만, 그 문서를 판마다 고쳐 두는 것은 내 일이었다. 이 일을 없애려고 MCP 서버를 각자의 PC 에서 꺼내 서버 한 대로 올렸다.

올리고 나니 그 일들이 거의 사라졌다. 판이 바뀌어도 공지를 보내지 않는다. 서버만 올리면 다음 세션부터 모두가 새 판을 쓴다. 새 사람은 셋업 페이지 하나만 받고 바로 팀 AX 환경에 들어온다. 사내 시스템 계정은 대시보드 한 곳에서 관리하고, 등록은 토큰 하나로 두 줄이면 끝난다. 권한 통제와 호출 기록은 따로 만들려던 것이 아닌데 덤으로 따라왔다.

## '업데이트해 주세요' 를 보내지 않는다

10월의 어느 날, 사내 MCP 서버의 판이 하루 동안 몇 번이나 바뀌었다. 팀 일정 조회, 회의실 예약, 경비 청구 툴이 차례로 붙던 날이다. 그날 나는 팀에 아무 공지도 하지 않았고, 아무도 아무것도 다시 깔지 않았다. 다음 세션을 연 사람에게는 새 툴이 그냥 있었다.

전에는 판이 바뀔 때마다 공지가 나갔다. 각자 토큰을 셸에 올리고 설치 스크립트를 다시 돌린 뒤 세션을 새로 열어 달라는 내용이다. 공지를 보내도 누가 따라 했는지는 알 수 없었고, 판이 바뀌면 셋업 문서도 같이 고쳐야 했다. 나중에는 로컬 서버가 새 판이 나왔다는 사실을 세션의 첫 응답에 덧붙여 알리게까지 했다. 그래도 받아 까는 것은 각자의 몫이었다.

서버가 한 대면 배포 한 번이 모두의 업데이트다. 플러그인도 세션을 열 때 스스로 올라간다. 손이 가는 경우는 하나 남았다. 훅이 쓰는 작은 바이너리가 뒤처지면 세션이 먼저 알려 주고, 그때 설정 명령을 한 번 더 친다. 옛 방식은 남겨 두지 않았다. 에이전트가 이틀에 걸쳐 원격 서버를 세우고 로컬 서버와 설치 스크립트 수천 줄을 지웠다.

## 새 사람은 바로 팀 AX 환경에 들어온다

새로 온 사람에게 이제 건네는 것은 셋업 페이지 하나다. 페이지는 명령 네 개로 시작하고, 그 아래에 "아래는 막혔을 때만 본다" 고 적혀 있다. 대시보드에 로그인해 쓸 시스템 계정을 넣고 토큰을 받는다. 두 줄을 붙인다. 세션에서 설정 명령을 친다. 재시작한다. 팀이 쓰는 MCP 툴과 공유 지식 저장소, 팀 공통 플러그인과 규칙이 한꺼번에 붙는다. 문서의 소요 시간 칸에는 10분이라고 적혀 있다. 끝났는지는 `claude mcp list` 에 두 서버가 `Connected` 로 뜨는지로 본다. 전에는 설치된 바이너리를 직접 띄워 자격증명 파일에서 변수를 몇 개 읽었는지와 켜진 서비스 목록을 출력으로 맞춰 봤고, 지식 저장소는 진단 명령을 따로 돌렸다.

전에는 300줄짜리 README 를 위에서부터 읽었다. 선행 조건 네 가지를 갖추고, 설치 스크립트로 여덟 단계를 돌리고, 자격증명 파일에 값 열한 개를 손으로 채웠다. 그중 몇 개는 어디서 받는지 팀에 물어야 했다. 윈도우는 스크립트가 따로였다. README 의 상당 부분은 함정 목록이었다. 임시 파일 이름이 같은 기계의 다른 계정과 부딪히면 다운로드가 멈췄고, 셸이 bash 가 아니면 설치 명령이 문법 오류를 냈고, PowerShell 버전이 낮으면 안내 문구의 한국어가 깨진 채 설치됐다.

지금은 그런 함정이 생길 자리가 없다. 기계에 깔 것이 거의 없고, 등록 두 줄은 리눅스, 맥, 윈도우에서 똑같고, 관리자 권한을 묻는 단계도 없다. 옛 방식으로 쓰던 사람들은 한 번 이사를 했다. 이사 페이지의 소요 시간은 20분이었다. 쓰던 값을 대시보드로 옮기고, 옛 설치가 남긴 MCP 등록과 플러그인, 바이너리, 설정 폴더와 캐시, git 자격증명 파일 속 토큰, 사용자 지침 파일에 끼워 둔 안내 블록까지 지운 뒤 새 사람과 똑같이 두 줄을 붙였다. 한 사람의 기계에 옛 방식이 그만큼 퍼져 있었다.

## 계정은 대시보드 한 곳에서

비밀번호를 바꾸는 날, 전에는 노트북의 자격증명 파일을 고치고 개발 서버에 접속해 같은 파일을 또 고쳤다. 이슈 트래커를 새로 쓰기로 한 날도 쓰는 기계마다 값을 넣고 세션을 다시 붙였다. 어떤 시스템은 값을 넣어도 툴이 조용히 안 떴다. 등록 명령에 따로 줘야 하는 인자가 있었기 때문이다.

지금은 대시보드의 사내 시스템 계정 칸을 한 번 고친다. 길어야 10분 뒤 새 세션부터 모든 기계가 새 값을 쓰고, 새로 넣은 시스템의 툴이 보인다. 칸마다 그 값을 발급하는 페이지로 가는 링크와 입력 예시가 붙어 있어서, 어디서 받는지 칸 안에서 바로 찾아간다. 홈 화면은 아직 넣지 않은 시스템이 몇 개인지 세어 보여 준다. 입력 칸은 넣는 순간 형식을 검사한다. 메신저 알림 주소라면 정해진 호스트와 경로인지, 같은 방이 두 번 들어가지 않았는지를 보고, 틀려도 오류 메시지에 주소를 그대로 찍지 않는다. 넣은 비밀번호는 다시 보여 주지 않는다. 서버는 호출이 올 때 그 사람의 값을 받아 메모리에만 들고, 에이전트는 비밀번호를 한 번도 보지 못한다.

## 등록은 토큰 하나로

토큰은 대시보드에서 한 번 받는다. 받을 때 쓸 곳을 체크하면 발급 화면이 쓸 곳마다 등록 명령을 한 줄씩, 토큰까지 채워서 내준다. 우리 팀은 사내 시스템용 MCP 와 팀 지식 저장소 두 곳에 붙으니 두 줄이고, 두 줄 모두 같은 토큰이다.

```bash
claude mcp add --transport http --scope user <name> https://<host>/mcp \
  --header "Authorization: Bearer <token>"
```

토큰이 샌 것 같은 날도 할 일이 하나다. 그 토큰을 폐기하면 다음 호출부터 막힌다. 새로 받아 두 줄을 다시 붙인다. 전에는 비밀번호 파일 하나가 여러 시스템을 다 열었으니, 새면 시스템마다 비밀번호를 바꿔야 했다. 지금은 토큰만으로는 비밀번호를 꺼낼 수 없다. 금고에서 값을 꺼내려면 사람의 토큰과 꺼내 가는 서비스 자신의 키가 둘 다 있어야 하기 때문이다. 토큰 모양은 GitHub 과 GitLab 의 개인 토큰을 그대로 따랐다. 발급 직후 한 번만 보이고, 목록에는 마지막 사용 시각과 최근 사용 주소가 붙는다. 값을 놓쳤으면 다시 볼 방법은 없고 재발급한다. 재발급은 같은 이름과 범위로 새 값을 만들면서 옛 값을 같은 순간에 폐기한다. 내가 공개해 둔 [engram](https://github.com/poorants/engram) 은 토큰 대신 브라우저 로그인 한 번으로 같은 등록을 끝낸다.

## 권한과 기록은 덤으로 따라왔다

서버가 요청마다 토큰으로 사람을 확인하다 보니, 사람마다 보이는 툴이 달라졌다. 계정을 넣은 시스템의 툴만 목록에 있다. 쓸 수 없는 툴을 문서로 막을 필요가 없다. 세션은 그 세션을 연 토큰의 주인에게 묶이고, 서버는 매 호출마다 둘이 같은지 다시 본다. 남의 토큰으로 이미 열린 세션에 올라탈 수 없다는 것은 테스트로 고정해 두었다. 누가 팀을 떠나면 계정을 막는다. 그 사람의 토큰은 다음 호출에서 전부 거절된다.

호출도 남는다. 어제 맡긴 이슈 정리가 어디까지 갔는지 궁금하면 대시보드의 호출 기록을 연다. 어떤 툴을, 어떤 결과로, 어떤 대상에, 어느 주소에서 불렀는지가 시간순으로 있다. 대상이 식별자로 남아서 어느 이슈에 댓글을 달았고 어느 문서를 고쳤는지까지 보이고, 주소 칸에는 서버가 아니라 내 PC 의 주소가 찍힌다. 문서 본문 같은 내용은 남기지 않는다. 전에는 이런 기록이 팀 어디에도 없었다. 내가 부르지 않은 호출이 보이면 그 토큰을 바로 폐기한다.

## 대신 생긴 불편

원격 서버는 내 PC 의 파일에 닿지 않는다. 빌드 산출물을 파일 서버에 올리라고 하면, 에이전트는 툴을 부르고 5분 안에 한 번만 쓰는 주소가 든 curl 명령을 돌려받아 내 셸에서 실행한다. 사람이 보기엔 한 번의 부탁이지만 안에서는 호출이 두 번이 됐다. 혼자 쓸 때 문제없던 로그인 세션 캐시도 껐다. 여럿이 같은 서버를 쓰면 그 파일 하나로 한 사람의 로그인이 다음 사람에게 넘어갈 수 있다.

로컬 MCP 는 로그인 없이도 괜찮았다. 비밀번호는 내 홈에 있고 부르는 것도 나였다. 서버로 올리면 그 전제가 사라지니, 서버는 호출마다 상대가 누구인지 묻는다. 위의 편함도 불편도 거기서 나온다.

## 마무리

[MCP 서버에는 LLM 이 없다](/blog/mcp-server-has-no-llm/)에서 나는 상시 서버와 중앙 자격증명 보관은 규모가 커지면 그때 올리면 된다고 썼다. 해 보니 계기는 규모가 아니었다. 사람 수가 그대로여도, 업데이트 공지를 보내고 옛 판을 쫓고 셋업 문서를 고쳐 두는 일이 툴을 만드는 시간을 잡아먹기 시작한 순간이 그때였다.

[인수인계 없이 신규 합류자를 받은 이야기](/blog/onboarding-without-handover/)에서는 흩어진 비밀번호를 홈의 파일 하나로 모았고, 새 사람의 셋업을 에이전트가 대신 해 주었다고 썼다. 한 달 뒤 그 파일을 없앴고, 셋업은 에이전트가 없어도 될 만큼 짧아졌다. 쓰는 사람의 일은 사라진 것이 아니라 서버 한 곳으로 옮겨 갔다. 나는 그 편이 낫다고 본다. 한 곳에서 하는 일은 한 번 제대로 하면 된다.
