단위 테스트가 전부 초록불이었는데, 에이전트가 만든 결과물은 사람이 만든 것과 달랐습니다.

제품의 관리 콘솔을 MCP 도구로 감싸 에이전트가 다루게 하는 작업을 하고 있습니다. 도구도 화면도 각자의 테스트를 통과하고 있었지만, 정작 "두 경로가 같은 결과에 도달하는가" 는 어느 테스트도 확인하지 않고 있었습니다.

원인은 화면이 사람 대신 조용히 처리하던 층 — 기본값 주입, 입력 검증, 암호 스위트 해석 — 을 도구가 통째로 건너뛴 데 있었습니다. 같은 목적, 다른 경로였습니다.

그래서 값을 하나씩 맞추는 대신, 두 경로가 갈라질 수 없도록 그 규칙들을 폼·서버·도구가 함께 쓰는 단일 원천으로 합쳤습니다. 등가성이 '바라는 속성' 에서 '구조로 보장되는 속성' 으로 바뀌었습니다.

그러자 도구가 사람과 같은 경로를 지나게 되고, 에이전트가 도구로 밟는 검증이 사람이 손으로 하던 검증과 같아졌습니다. 수동 회귀 검증의 상당 부분을 에이전트에게 넘길 근거가 여기서 처음 생겼습니다.

에이전트에게 제품을 쥐여줄 때 진짜 어려운 문제는 도구를 만드는 것이 아니라, 그 도구가 사람과 같은 길을 걷게 만드는 것이라 생각합니다.
